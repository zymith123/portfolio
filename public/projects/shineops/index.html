ShineOps

Client retention and operations software for recurring cleaning businesses: it scores every client's health, tells the owner who's at risk and what to do about it, and turns that into a task someone owns.

Personal project 2026 Next.js · PostgreSQL · Claude

The problem

Residential cleaning companies live on weekly and biweekly recurring clients, and most cancellations come from quality problems the owner never hears about until it's too late — a different cleaner every time, a missed baseboard, a complaint that never got followed up on. ShineOps collects feedback from every channel, scores each client's health, and turns a drop before it becomes a cancellation into a task someone actually owns.

What I built

  • Owner dashboard — recurring revenue, revenue at risk, 30-day rating trend, visits this week, a list of clients needing attention, and a cleaner scorecard.
  • Client health scoring — every client is scored 0–100 (Healthy / At risk / Critical) from ratings, rating trend, complaint themes, skipped visits and cleaner consistency. With an Anthropic API key, Claude reads the client's actual feedback and writes the summary, reasons and a specific recommended action; without one, a deterministic rules engine does the same job.
  • Sales / call intelligence — calls arrive from the phone system with transcripts. AI classifies each call, summarizes it, pulls out the caller's details, scores the rep on a 5-part coaching rubric, and moves leads through the pipeline automatically; complaint and cancellation calls feed straight into the caller's health score.
  • Task queue — health alerts automatically become follow-up tasks, one open task per client, alongside client requests and manual tasks.
  • Clients, schedule & team — full client CRUD with recurring plans and pause/cancel/reactivate; visit generation from those plans; role-based access for Owner / Manager / Cleaner / Client.
  • Cleaner app & client portal — cleaners get a daily route with entry instructions and a heads-up on low-rated clients; clients see upcoming cleans, rate visits, and request a reschedule, deep clean or pause.
  • Platform admin — an operator console across every company on the platform: onboarding, user search, role changes, password resets.
  • Feedback webhook — accepts three payload formats (native, review-platform events, NPS surveys), normalizes and de-duplicates them, and re-scores health immediately.

Key technical decisions

  • Every AI feature has a deterministic fallback. Client health scoring and call analysis both run through Claude with structured, Zod-validated output when an API key is configured, but fall back to a rules engine if the key is missing or a request fails — the product keeps working either way.
  • Multi-tenancy enforced at the query level, not just the UI. Every row carries a company_id; every query and mutation is scoped to the signed-in user's company, and ids submitted from forms are verified to belong to that company before use.
  • Role checks start every server action. App mutations run through Server Actions that check the caller's role first; platform admins (who have no company) are enforced by a database check constraint and use a separate guard from company-scoped pages.
  • Sessions re-check the database on every request. Auth uses a signed, HTTP-only JWT cookie, but the user record is re-loaded from the database each time, so a deactivation or role change takes effect immediately instead of waiting for the token to expire.
  • Health alerts sync to a single owned task. Each client keeps at most one open health-related task that updates as the situation changes, rather than piling up a new task every time the score moves.
